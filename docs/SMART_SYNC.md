# AniRezik 0.3.2 — Smart Sync

Каталог сохраняет **30 704 ID** и все метаданные версии 0.3.1. Полного повторного импорта не было. Контрольная точка Git: `checkpoint/v0.3.1-before-smart-sync`; изменения разрабатываются в `codex/smart-sync-0.3.2`.

## Обслуживание и полный аудит

`npm run sync:anime` теперь выполняет maintenance вместо популярного топа. `--target` больше не поддерживается. Старый `syncCatalog` оставлен как совместимый инструмент ограниченного первоначального импорта и для прежних регрессионных тестов; его maxTitles ограничивает обновляемую выборку, а не итоговый каталог. CLI его не вызывает.

За один день maintenance рассматривает недавно созданные записи (created_at_desc, до 8 страниц, ранняя остановка после второго известного пакета), изменённые записи (updated_at_desc, до 8 страниц), текущий и предыдущий сезоны (до 12 страниц каждый). Остальной бюджет выделен активным/анонсированным/приостановленным и выпускам последних 180 дней: адресные пакеты по 50, вращающийся курсор. Сюда входят фильмы, OVA/ONA и specials; фильтра рейтинга/типа нет. Не более **80 логических пакетов** по умолчанию, один последовательный запрос в секунду. Сетевые повторы API ограничены двумя на пакет: при отказах возможны дополнительные попытки, это не обещание ровно 80 HTTP-запросов. Лимиты окон видны в `catalog-maintenance.json`; ежедневный режим не гарантирует обнаружения всех исторических изменений за сутки.

Ключ кеша включает UTC-день, query, variables и origin. Повтор после сбоя использует валидированные пакеты дня; повтор завершённого дня начинает с прежнего курсора. Новый день проверяет следующую группу активных записей. Промежуточный checkpoint — `.cache/shikimori/maintenance-progress.json`, завершённое состояние — `src/data/catalog-maintenance.json`. При ошибке API/структуры/дублях снимок не записывается. Пустой discovery считается ошибкой, пустой сезон допустим. Отсутствующие в частичном ответе ID не удаляются.

Полный аудит (`npm run sync:full`) оставляет прежний прямой и обратный обход, проверку связей, кеш/возобновление/Retry-After. Лимита 5000 тайтлов нет. Дополнительно падение обнаруженного охвата более 5% блокирует замену. Старые записи сохраняются даже при меньшем допустимом охвате. Смена стабильных ID/slug/legacyIds, потеря описаний, дубли, смена политики и аномальный прирост блокируют автоматическое применение. Требующие проверки большие изменения остаются для ручного разбора.

## Бесплатная автоматизация

В `sync-anime.yml`: ежедневно 17:30 UTC maintenance, первого числа 18:30 UTC full audit, ручной выбор режима. Синхронизация пока **не включена**: регистрация OAuth-приложения владельцем не подтверждена. Проверенная 24.10.2026 [официальная документация](https://shikimori.io/api/doc) требует имя OAuth2 Application в User-Agent и запрещает маскироваться браузером. API-права и права на изображения — разные вещи.

Владельцу:

1. Войти в Shikimori и создать своё приложение на https://shikimori.io/oauth/applications; указать AniRezik и публичный адрес сайта, следуя действующей форме источника.
2. GitHub → anirezik → Settings → Secrets and variables → Actions → Variables → New repository variable: `SHIKIMORI_USER_AGENT` = точное зарегистрированное имя приложения. Секрет клиента для публичных метаданных этому коду не требуется; не публиковать его в переменной/репозитории.
3. Создать `SHIKIMORI_SYNC_ENABLED` = `true`. Не включать до регистрации/проверки условий API.
4. Actions → Refresh anime metadata → Run workflow → main → maintenance. Проверить отчёт и все jobs. После первого успеха расписание работает автоматически.

Цепочка: sync → metadata-only guard → artifact снимка → общий reusable Pages workflow → check/build/unit → Chromium/Firefox на Ubuntu и WebKit на macOS → повторный guard → обычный fast-forward push только трёх разрешённых файлов данных → deploy того же проверенного artifact. Обновления кода/workflows/реестров прав так не коммитятся и не сливаются. При движении main после начала прогона публикация данных отклоняется. Если branch protection запрещает push бота, workflow остановится; защита не отключается. Кеш сохраняется отдельным always-step и после неудачного sync. Не добавлены PAT, платный сервис или обязательный сервер.

Обычный push с GITHUB_TOKEN не вызывает новый push-workflow ([GitHub Docs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)). Поэтому проверка и deploy вызываются в том же запуске через reusable workflow; ожидания несуществующего второго запуска нет. При любых ошибках проверки опубликованный сайт остаётся прежним. Полная статическая сборка намеренно остаётся воспроизводимой; инкрементальное повторное использование непроверенных HTML не введено.

## Размер и изображения

catalog.json: **59 967 065 → 45 211 278 байт (−24,6%)**. Убраны только форматирующие пробелы, структура schemaVersion:2 прежняя. До/после проверено полное deep equality, не только ID. Compact writer используется обоими режимами sync; Prettier исключает snapshot. Копирование/rename/previous backup сохранены. Добавлять ещё один двоичный формат ради небольшого дополнительного выигрыша не потребовалось. Браузер по-прежнему не скачивает catalog.json.

Поиск: общий индекс **5 933 420 байт JSON / 2 341 345 байт gzip**, распаковка/поиск в Worker. Изменения только упаковки snapshot не меняют индекс. Подробности и карточки по-прежнему в отдельных пакетах; 3000 SEO-страниц и универсальный маршрут сохранены.

Динамические карточки сначала создают разметку с заглушкой. IntersectionObserver (160 px) запрашивает нужный image-package и раскрывает изображение. Общая очередь ограничивает все параллельные package-запросы тремя, успешные пакеты переиспользуются. Ошибочный пакет даёт заглушку и 30-секундную паузу, без автоматического повтора. Отсоединённая карточка не меняется после позднего ответа. Старые worker-ответы игнорируются ещё до загрузки изображений. Поиск загружает максимум шесть показанных результатов, детали — один пакет. Повторные документы используют обычный HTTP-кеш по правилам хостинга/CDN.

Точные mainUrl/originalUrl обновляются при получении свежей записи sync. URL не собираются, случайных cache-buster нет. До истечения обычного HTTP-кеша старый пакет может ещё обслуживаться браузером. Карточки/blur используют mainUrl, детали originalUrl; если доступен один вариант, он заменяет отсутствующий. Разрешённый широкий фон сохраняется.

Публичный Shikimori остаётся unknown и **выключен**. Область разрешения теперь машинно проверяется: scope.kind = none / all / ids / urls; animeIds либо точные urls. Без явного all нет разрешения на весь источник. URL-ограничение не переносится на новый хеш или original другого файла. expiresAt отклоняет истёкшее/некорректное подтверждение при сборке; статический хостинг требует своевременной пересборки при отзыве/истечении прав. Неизвестные/просроченные права не активируются новой сборкой. Нужны настоящее evidence, разрешение hotlinking и browserCaching, атрибуция, origins и точный охват. Коммерческое использование отдельно не подтверждено. Локальный `dev:posters` сохранён; это не публичная лицензия.

## Провайдеры видео

`providers/video/updates.ts` — отдельный контракт дельт доступности серий/озвучек с собственным курсором и merge после проверки provider rights, origins, регионов и номера серии. Он не использует episodesAired Shikimori как признак готового видео. Частичная дельта не удаляет прежние серии; сетевой отказ не меняет снимок. Ни одного адаптера/расписания для неразрешённого провайдера не включено. Реальные условия удаления/доступности, авторизацию и лимиты реализует будущий согласованный адаптер; архитектура не обещает готовую интеграцию AniLiberty/AniDUB.
